## Summary

Three couplings, one slice, one outcome: **a specification generated by a real container.**

`engine-adapters/speckit` today is simultaneously the specification engine, the AI-agent invoker, and
the (unimplemented) container driver. This epic separates the three into contracts that a build
failure defends, implements the container driver behind the middle one, and ends at quickstart `V13`
— the scenario that has never run.

**The sequencing constraint that shapes everything below**: `T447` is the only task that requires
Docker, and RAID **R-04** says container-in-container is not available in CI. So every other task
must be provable without a container, and `T447`'s verification is explicitly split into a mocked
half that runs in CI and a manual half that does not. Pretending otherwise is how EPIC-003 ended up
with 65 passing tests and an engine that cannot start.

**What this epic does not do**: build persistence (EPIC-029), BYOK (`D-41`), a real Cursor adapter
(`R-AI-005` uninvestigated), or anything with product surface.

## Technical Context

**Language/Version**: TypeScript 5.x, Node 22 LTS. Unchanged — Native §28 preserves both.

**Primary Dependencies**: none new at runtime. The Docker provider talks to the daemon over its HTTP
API via `undici` (already transitively present) or the Node built-in `fetch` — **decided in
[research.md](./research.md) `R-028-1`**, not assumed. No `dockerode`.

**Storage**: none new. `AgentRegistration` follows the `T463` precedent — a narrow delegate with
Prisma's shape — because **Prisma is still not a dependency** (EPIC-004 `T013`).

**Testing**: Vitest. Three new projects (`agent-contract`, `agent-adapters`, `execution-providers`)
must be added to the `test:unit` script explicitly. **The root script names projects one by one, and
the EPIC-003 closure report records what that hides**: *"an empty Vitest project passes silently when
sibling projects have tests"* — two projects collected nothing and the run stayed green while three
tasks were falsely marked complete. `T537` adds a guard for exactly this.

**Target Platform**: Linux containers; the worker process spawns them.

**Project Type**: monorepo packages + adapters. No UI, no API surface.

**Performance Goals**: none new. Existing per-job wall-clock, CPU, memory and pid caps are unchanged
and remain the only cost containment (PP-017, RAID **R-02**).

**Constraints**:
- `ADR-0002` holds for the `generation` profile, **byte for byte, with its existing test unmodified**
  (`SC-AGT-005`). An epic that widens a security boundary must prove which half it did not touch.
- `ADR-0001` is preserved. The engine contract does not change shape.
- RAID **R-04** — no container-in-container in CI. Shapes the whole verification strategy.
- `FR-AGT-012` / PC-3 — prompts and model output never enter operational logs.

**Scale/Scope**: 2 new contract packages · 3 new adapter/provider packages · 1 refactored engine
adapter · 3 architecture suites (2 existing, 1 new) · ~56 tasks.

**NEEDS CLARIFICATION**: none. **Four questions were answered on 2026-08-14** and all four confirmed
the recommendations below — recorded in [spec.md](./spec.md) *Clarifications*. `R-AI-001` and
`R-AI-002` remain open by decision: they gate the *capability* of the Claude adapter, not this epic's
structure, and the chosen path is to discover the answer by running a real container — see **The
honest limit** below.

## Build order

```text
F-28.1 workspace + test plumbing
        │
        ├──► F-28.2 execution-contract ──┐
        │                                 ├──► F-28.5 Docker provider ──► T447 ──► V13
        └──► F-28.3 agent-contract ──────┤                                          ▲
                     │                    └──► F-28.4 SpecKitEngine refactor ────────┘
                     │                                    │
                     └──► fixture agent ──────────────────┴──► F-28.6 architecture suite
```

**`F-28.2` before `F-28.3`** — the agent contract references `ExecutionSession`, not the other way
round. An agent runs *inside* an environment; the environment knows nothing about agents. Getting
this backwards would make the execution layer depend on the AI layer, which is the coupling the epic
exists to remove.

**The architecture suite lands last and gates everything.** It cannot pass until the refactor is
complete, and it is what makes the refactor irreversible.

```text
├── agent-contract/           # NEW — AgentGateway
└── execution-contract/       # NEW — ProjectExecutionEnvironment

worker/src/                   # composition root gains two registries
backend/tests/architecture/   # gains agent-independence.spec.ts
```

**Structure decision**: contracts in `packages/`, implementations in `<thing>-adapters/` or
`<thing>-providers/` — the convention `engine-contract` + `engine-adapters/` already established.
Two new top-level directories is more structure than a single shared package, and that is argued in
Complexity Tracking rather than assumed.

**`ContainerRuntime` moves out of `engine-adapters/speckit`.** It is currently declared inside the
adapter that uses it, which is why nothing else can use it. That move is the mechanical core of
`D-21`.

## Design decisions worth stating

### The four `claude` strings, and what replaces them

| Today | After |
|---|---|
| `specify init --integration claude` | `--integration ${agent.descriptor.specKitIntegrationName}` |
| `['claude', '-p', '/speckit-tasks']` | `agent.execute({ capability: 'generate', command: '/speckit-tasks' }, ctx)` |
| `aiProviderToken: string` | `credentials: ScopedCredentialRef[]` on the execution request |

`SpecKitEngine` keeps its five ordered invocation steps and its parsing. **What leaves is the answer
to "who reasons" and "where does it run".** The step ordering, the `E7` pre-flight refusals, and the
failure taxonomy are unchanged — those are engine concerns and `ADR-0001` protects them.

### Failure taxonomy: reuse, do not re-invent

The agent and execution contracts reuse the shape of `EngineFailure` — a closed reason enum, a
user-safe `message`, an operator-only `diagnostics`, and **no `unknown` member**. The engine
contract's comment states why, and it applies unchanged: *"a generic failure is a defect, not a
fallback."*

Three reasons carry forward with hard-won meaning, all from the EPIC-003 conformance suite:
`cancelled` must never be reported as `timeout`; `engine_unavailable` must mean the runtime is
unreachable and not that the caller was misconfigured; a hung step self-terminates.

### `T449` — resolving the duplicate registry, finally

`worker/src/engine-composition.ts` defines its own `EngineRegistry` alongside
`backend/src/modules/engines/engine-registry.service.ts`. Two implementations of `FR-021` that can
disagree. `T449` has been open since 2026-08-08 with no owner.

**Decision: the backend service owns capability validation; the worker registry delegates to it.**
The backend's version is the one `EnginesModule` wires and the one with 20 tests. Adding two more
registries (agent, execution) while a duplicate persists would triple the problem, so it is fixed
*before* the new registries land, not after.

### The honest limit

`R-AI-001` and `R-AI-002` are **uninvestigated**: nobody has verified that `claude -p /speckit-specify`
inside a container is a supported server-side execution model. This epic's structure does not depend
on the answer — the contract is provider-neutral by construction. **Its `SC-AGT-001` does.**

If the first real container reveals the invocation does not work as mocked, `SC-AGT-001` fails for a
reason no amount of design prevents. That is the correct outcome: it is the finding EPIC-003 could
not produce because it never started a container. Recorded here so it reads as a discovery rather
than a failure of this plan.

## Complexity Tracking

| Violation | Why needed | Simpler alternative rejected because |
|---|---|---|
| **Two new top-level directories** (`agent-adapters/`, `execution-providers/`) | Mirrors `engine-adapters/`, and the ESLint boundary rules key off directory names — a rule that says "backend may not import `agent-adapters/*`" needs the directory to exist | Putting adapters under `packages/*` is simpler, but then the boundary rule cannot distinguish a contract from an implementation, and the whole enforcement mechanism rests on package naming discipline |
| **Two new contract packages rather than one** | Native §3 forbids merging abstractions of different kinds, and the dependency runs one way: agent → execution, never back | One `packages/runtime-contract` is fewer moving parts. It would let the execution layer see agent types, which is the coupling this epic exists to remove — repeated at a new seam |
| **`T447` verification split across CI and manual** | RAID **R-04**: container-in-container is unavailable in CI. A single task would be marked complete on mocked evidence | Asserting the driver only against a mock. That is precisely how EPIC-003 shipped an engine that cannot start, and the closure report says so |
| **Constitution VIII deviation** — fourth occurrence | Branch is `epic/003-specification-engine`; EPIC-003 has uncommitted work that branching would drag along | Branching first remains correct and did not happen. Not justified — recorded. `D-39` proposes the check that would catch it |
