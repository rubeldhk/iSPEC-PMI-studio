# DEF-029-005 — a captured requirement does not appear in the register until a filter changes

**Originating task**: T885 (found while capturing a requirement by keyboard against the running app)
**Found**: 2026-08-22
**Status**: OPEN — **not an EPIC-029 defect**; recorded here because it was found here, and
proposed for deferral to **EPIC-011** (requirement register) at T904 triage

## Reproduction

1. Open a project, type a description into **New requirement**, press Save.
2. The requirement **is** created — verified against the API during the run:

```json
{"projectFound":true,"requirementCount":2,
 "first":{"reference":"REQ-001","description":"The system shall record a keyboard-only accessibility pass.","type":"functional","priority":"p2"}}
```

3. The register above the editor continues to display the empty state — *"No requirements match. /
   Nothing in this project fits the filters above — clear one to widen the search."*
4. Changing any filter re-queries and the requirement appears.

## Expected vs actual

Expected: after capturing a requirement, the user sees it in the register. Actual: the user sees
an empty state telling them nothing matches, immediately after they added something that does. The
data is correct; the screen contradicts it.

## Cause

`RequirementsPage`'s fetch effect depends on `[api, projectId, type, priority, status]`
(`frontend/src/pages/Requirements.tsx`). Saving does not change any of them —
`RequirementEditor.onSaved` returns the shell to the same view — so the effect never re-runs and
the list keeps its stale result. Filtering is a **query of the API** by design (EPIC-011, `FR-008`),
so there is no client-side list to update either.

## Why this is not EPIC-029's defect

The design system made it *more* visible, not more likely: the restyled empty state states its
reason confidently ("Nothing in this project fits the filters above"), where the previous bare
`<p>No requirements match.</p>` was easier to overlook. The stale-list behaviour predates this Epic
and belongs to the register's own requirements.

`FR-DS-021` is nonetheless the reason it reads so wrong: an empty state that explains itself is
worse than a blank area when the explanation is false. Whoever fixes this should treat "the empty
state must not be reachable while data exists" as part of the fix.
