# DEF-029-008 — the Table component is called by no delivered page

**Originating task**: T918 (the tools bar); found by the `T927` reachability run
**Found**: 2026-08-24, while looking for `.ds-table__tools` in the running application and not finding it
**Status**: OPEN — disposition belongs to `T904` triage; **proposed for deferral**, see below

## Reproduction

Sign in, open a project, and inspect the requirement register in the running application:

```js
!!document.querySelector('.ds-table')        // true
!!document.querySelector('.ds-table__tools') // false
```

Then grep the source:

```console
$ grep -rl "from '.*design/components/Table'" frontend/src frontend/tests
frontend/tests/unit/a11y/components.spec.tsx
frontend/tests/unit/design/fixtures/NewPage.tsx
frontend/tests/unit/design/prototype-parity.spec.tsx
frontend/tests/unit/design/state-coverage.spec.tsx
frontend/tests/unit/design/structure.spec.tsx
```

**Five importers, every one of them a test.** No file under `frontend/src` imports `Table`.

## What is actually going on

This is **not** an oversight, and the reason is documented at `frontend/src/pages/Requirements.tsx:7`:

> *Select filters over a plain `<table>` rather than the design system's self-filtering Table — its
> filter narrows rows already fetched, and this page's contract is that the DATABASE narrows them.*

The register's filtering is a query (`listRequirements`, `SC-009`'s 1-second p95 over indexes), so
the page cannot use a component whose filter sieves rows already in the browser. Traceability and
Projects render no table at all. So `Table` has exactly one delivered consumer that *could* use it,
and that consumer has a correct reason not to.

The CSS half does reach the page: `Requirements.tsx` applies `.ds-table`, so the `T918` column
header treatment was observed live in the `T927` run (`textTransform: uppercase`). It is the
**component** — and with it the tools bar, the loading/error/empty branches and the built-in
filter — that nothing calls.

## Why it is recorded rather than shrugged at

This is the seventh **built-tested-called-by-nothing** in this programme, and the third inside this
Epic alone (`T866a`'s stylesheet import, `T913`'s theme wiring, `T914`'s shell controls). Every
check in the Epic passes on it: `T886` state coverage renders it in a test, `T894` axe-scans it in
a test, `T900c` composes it into a fixture page — all in tests. Constitution XI exists precisely
because a component can be perfectly correct and reach no user, and `Table` is currently that.

`T918` made it worse in the narrow sense that it added a tools bar nobody sees. The honest reading
is that `T918` did not create the problem, it revealed it.

## Proposed disposition — defer, with the choice named

Two defensible resolutions, and **neither is EPIC-029's to make**, because both are decisions about
a register screen this Epic does not own (`PMI-DOC-005` `RULE-03`):

1. **Give `Table` a server-filter mode** — the caller supplies `onFilterChange` and the component
   stops sieving. Requirements then adopts it and the whole inventory row is live.
2. **Accept that `Table` serves future screens** and record it — several declined prototype
   patterns (Decision Inbox, the specification registry) are client-filterable grids that would use
   it as built.

Option 1 is the better answer if the register is the only table the platform will ever have;
option 2 is better if it is not. **EPIC-011** owns the requirement register and **EPIC-010** owns
the specification interface; the choice belongs to whichever reaches a second table first.

Until then the component stays built, tested and unreferenced — which is a known state, recorded
here, rather than a surprise for whoever opens the file next.
